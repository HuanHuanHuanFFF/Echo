# 渐进式取证、MMR与重排调研

日期：2026-09-19。状态：用户要求的单个Luna/max子线程调研已完成，主线程核对官方资料与固定提交源码，并完成一个本地输出格式统计。以下是建议，未实现或确认为新默认；没有新模型调用、索引重建或召回参数实验。
承接[最终集诊断](../evals/2026-09-18-dense-hybrid-diagnosis.md)、[基线](../project/baseline.md)与[Agent MCP契约](../development/phase-04-agent-mcp.md)。本报告不恢复旧调研中的专用read、远程读取或引用链导航；补读仍由Agent使用宿主文件工具完成。

## 结论

可以采用“查询相关的候选预览 → Agent选择 → 按范围读原文”。这可以减少首轮进入主Agent的内容，但不保证累计token下降，也不能让只看标题的选择自动变准。
当前更值得改变的是候选选择和证据获取流程；已测数值的局部收益较小，不能称为全局调参极限。此前缺失锚点都在候选并集中，主要被同篇3块/topk门控挡住；继续盲目扩大候选或细扫RRF不是首要方向。

检索数量、精排数量、交给主Agent的正文数量是三件事。服务端可以处理较多候选，只向主Agent返回少量证据；引入独立reranker会有额外推理成本，不能把它算成“没有处理这些文本”。

## 外部方案实际做了什么

| 方案                                   | 可核查实现                                                                | 对Echo的意义与限制                                                                                 |
| -------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| QMD                                    | query给docid、路径、标题、短原文snippet与绝对行号，get可按起始行/行数读取 | 最接近预览后按需原文；Echo可用现有宿主读取完成第二步。外部实现存在，不代表Echo已获得节省或精度收益 |
| LangChain MultiVector / ParentDocument | 子片段先检索，从doc_id收集父文档，再从docstore立即返回父文档              | 小块定位、大块补上下文；并非Agent先选再读，父文档很大时会增加输入                                  |
| LlamaIndex AutoMerging                 | 足够多子节点命中时换成父节点，也可补齐相邻节点间的缺口                    | 适合边界/上下文缺失；自动合并不等于省token或保留Echo原文行号契约                                   |
| Qdrant MMR                             | 在候选中逐个选取，平衡查询相关性与相对已选内容的差异                      | 控制重复和多样性；不是问答完整性判断，也不要求Echo更换SQLite                                       |

## MMR、RRF、rerank的区别

- RRF融合多路的名次，奖励两路都靠前的候选；当前Echo已实现。
- MMR的直觉是“与问题相关，同时尽量不重复已选内容”。多样性不是事实互补性的证明；同篇两段很像，却可能分别包含必须同时读取的条件和例外。
- rerank让专用模型同时看问题与片段，重新判断相关程度；它不等于生成答案，分数也不是“答案一定存在”的概率。

MMR通常需要比最终输出更多的候选才能改变集合；候选数等于输出数时主要只能改变顺序。对Echo，可复用已有向量在本地计算相似性，但怎样与RRF分数结合、保留子问题覆盖，需要单独验证，不能直接照抄一个lambda。
如果每篇3的硬限制仍然提前删掉候选，无论MMR还是rerank都没机会挽回；应在保留完整候选的前提下比较选择方式，最终仍尊重用户指定上限。

Anthropic也公开了“先较多候选、再rerank、再送少量正文”的流程，其[Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)还在建索引时给chunk补充文档语境。这种建索引改造与输出预览是不同层次；官方组合成绩使用其语料、模型和预算，不能当作Echo已经获得的效果。

## 建议的Echo交互形状

```
Agent提供自包含的问题/子问题
  → Echo召回、融合，保留未返回候选
  → 可选候选选择改进（先单独验证rerank或MMR）
  → 少量直接证据 + 查询相关的短预览
  → Agent按路径/范围用宿主工具补读
  → 证据不足时明确改写、过滤或扩大参数，再检索
```

这是主线程建议，不是已决定的默认流程。简单问题可以一次返回足够证据；复杂问题再继续，避免所有请求都强制增加一次往返。
Anthropic官方[按需上下文/渐进披露说明](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)支持保留轻量路径等引用、运行时按需读取的模式，也明确指出探索增加延迟且可能走弯路。

预览建议包含稳定来源、路径、标题层级、原文摘录与行范围，必要时标明对应子问题。不要只给文件名或生成摘要；README等同名文件和同标题下不同事实都可能无法区分。预览只是选择线索，具体事实、数字、代码条件仍需足够原文支撑。
不连续摘录必须分别标范围，不能拼接后冒称连续原文；短预览不能切掉否定或条件后仍当作完整证据。生成摘要如以后采用，应明确是派生内容，并保留原文入口。

预览若只是把当前已经裁剪后的10块缩短，仍看不到因同篇上限跳过的第4块。应保留候选并提供继续探索的入口；Agent显式决定扩大topk、单篇数量或预算。游标跨页累计语义、硬预算数值、超限处理仍在讨论，本报告不定案。

同文命中可按路径归组显示多个章节/片段，帮助Agent挑选，但不能把“每文档只留1条”当成通用策略。补读优先限定章节或邻近窗口，不自动拉回整篇长文。索引后原文发生编辑的边界仍按已有成功同步前提处理，不新增强一致承诺。

## 是否已到调参极限，以及下一步

不是全局极限。现有实验只能支持在已测组合里进行选择；没有证明其他配置、切块或模型无法更好。但当前更有价值的方向是流程改进，继续大规模组合RRF/权重/预算不符合已发现的首要瓶颈。

建议顺序：

1. 固定检索，先验证紧凑输出与“预览＋窄窗口补读”，让Agent显式控制扩大范围。
2. 补齐子问实体/条件要求，作为Agent使用契约，不让Echo承担自动问题拆分。
3. 固定候选和其余参数，分别做一个rerank对照和一个MMR对照，先不叠加。模型/凭据/正文外发/费用在决定实施时确认。
4. 分开报告首轮输入、单次最大输入、全轮累计输入、读回次数、原文证据恢复、引用和答案正确性。仅短卡片的字数下降不构成准确或省钱的结论。

真正的卡片选择和多次补读必须跑Agent流程；当前固定单轮召回脚本无法替它验收。已查看的最终200题可保留诊断记录，若继续据其挑选新方案，就不能再宣称是新方案的盲测；最终验证需新的留出材料。
本轮只新增调研文档与统计指纹，不修改生产接口、默认配置、个人笔记或任何索引；不运行新模型/检索实验，不新建PR或合并。
