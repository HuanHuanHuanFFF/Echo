## 多模型与切块策略隔离

- 同一个 SQLite 数据库可同时保留多套切块策略的索引；不同策略分别保存 chunk 和对应 BM25 索引。
- 每套切块策略下可同时保留不同 embedding 模型、不同向量维度的向量索引，切换时不以新模型覆盖其他已建立的模型索引。
- 向量表命名采用“模型 ID＋向量维度”的方向，同时体现所属切块策略的隔离关系。具体命名、名称合法化及配置指纹的冲突处理在集中实现时落定。
- 召回参数不按模型或切块策略再分组保存。RRF 权重、候选量、topk、单篇上限等仍是查询设置；在同一套 chunk 上调参不应产生新的索引副本或重新切块。
- embedding 继续由用户配置 API/key；BM25 继续使用本地算法。

## 策略目录与 ID（用户已确认）

切块规则集中放在一个策略目录中，Echo 从目录发现策略；实现文件的文件名（去掉扩展名）必须与策略 ID 一致。新增规则通过增加策略文件完成，不要求修改 Echo 核心的策略列表。

## 配置分离与指纹（用户已确认）

- 切块配置单独放一个目录；模型配置单独放另一个目录，不再将所有配置档混在一个主文件中。
- 模型名、向量维度、服务 URL、API key 的配置归属属于同一个模型配置档。
- 用户确认：通过策略 ID 选择切块实现，内部另记代码、版本及实际生效参数的指纹，防止同名策略变化后误用索引。

## 具体方案（实施草案）

以下是依据上述需求细化的方案，字段名及迁移细节尚未作为已实现契约发布。

### 1. 文件组织与加载

建议目录如下。目录名、配置字段和其余全局文件的拆分属于实施草案：

```text
chunkers/                         # 切块规则实现
  echo-heading-lines.mjs
  paragraph.mjs
config/
  chunking/                       # 切块配置档
    heading-1000.json
    heading-500.json
    paragraph-default.json
  embedding/                      # 模型配置档
    model-a-1024.json
    model-b-768.json
  retrieval.json                  # 一份共用的召回设置
  lexical.json                    # 本地分词设置
echo.config.json                  # 入口、默认选择、数据源与运行设置
```

区分两个 ID：策略 ID 指实现文件，例如 echo-heading-lines；切块配置 ID 指一组参数，例如 heading-1000、heading-500 都引用 echo-heading-lines。实现文件名必须等于策略 ID；建议配置文件名同样等于该配置档 ID。内部使用生效内容指纹，重命名配置档本身不应重复建立相同索引。

沿用现有自定义模块接口，每个策略默认导出 id、version、chunk(input)。文件名用于发现与定位，加载后校验导出 ID；仅导入选中策略，不为列出文件而执行全部模块。建议首版加载 .mjs，TypeScript 策略先编译到该目录；内置策略随 Echo 分发，安装后的默认目录定位在构建时验证。

切块配置示意（config/chunking/heading-1000.json）：

```json
{
  "id": "heading-1000",
  "strategy_id": "echo-heading-lines",
  "options": {
    "max_chars": 1000
  }
}
```

模型配置档包含 id、model、dimensions、base_url、API key 引用，以及 timeout_ms、batch_size、send_dimensions、document_prefix、query_prefix。凭据引用继续沿用现有 api_key_env：归属在模型配置内，实际 key 从环境变量读取；key 不参与索引指纹。

其余配置建议：

| 文件                  | 职责                                                                          | 变更影响                                                    |
| --------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------- |
| retrieval.json        | mode、RRF、候选量、标题权重、相似度阈值、topk、单篇上限、输出预算             | 搜索时生效，不复制 chunk 或向量；所选检索模式仍须有对应索引 |
| lexical.json          | 分词 locale、自定义词典                                                       | 更新相应 BM25 索引；分词本身不改变 chunk 或 embedding 输入  |
| echo.config.json      | 数据库路径、Markdown 数据源、各配置目录及默认切块/模型配置 ID、服务超时与并发 | 选择组合及运行环境；数据源变化需同步                        |
| evals/ 下已有评测文件 | 语料、问题、标签、实验策略和累计预算                                          | 保持实验与运行配置分开                                      |

这版草案中，召回与分词各用一份全局文件，不引入按模型或切块策略保存多套召回配置。请求级 overrides 继续覆盖全局召回设置。入口通过 ID 引用切块和模型配置，不再内嵌它们的完整参数；具体 CLI/MCP 选择字段集中实施时落定。

配置目录由主入口指定，相对路径按声明它的配置文件目录解析。ID 只允许受限的字母、数字、短横线和下划线，不接受路径片段。拒绝缺失引用、重复 ID、文件名与导出 ID 不一致或无效模块。策略仍输出原文行范围，Echo 校验并提取证据正文。

### 2. 策略 ID 与索引版本

策略 ID 是方便用户选择的稳定名称；内部索引身份还要包含策略版本、实现内容和实际生效的切块参数指纹。否则同名策略从 1000 字符改成 500 字符后，会误用旧索引。

切块策略或其参数变化建立不同的切块索引身份；切回已建立且来源快照仍有效的配置时复用。外部模块依赖变化沿用提升策略版本的要求。分词配置另有指纹，不能让不同词典的 BM25 索引混用。召回参数不参与上述身份。

### 3. 索引分层

```text
SQLite
  切块策略 A + 版本/参数指纹
    chunk 与来源快照
    BM25（校验分词指纹）
    模型 A + 1024 维向量
    模型 B + 768 维向量
  切块策略 B + 版本/参数指纹
    chunk 与来源快照
    BM25（校验分词指纹）
    模型 A + 1024 维向量
```

向量表采用模型 ID、维度、切块索引身份及 embedding 配置指纹生成安全表名；登记表保存完整身份和实际表名的映射，并验证完整指纹，不能只依赖截短名称区分索引。同名模型在服务地址或输入前缀不同时也能隔离；API key 不作为索引身份。

模型配置集中声明、同步/查询选择其中一项；召回参数继续只有 retrieval 及单次 overrides，不复制进各策略或模型配置。具体多模型配置字段、CLI/MCP 选择字段在集中实施时统一落定。

### 4. 同步、查询与迁移

- 新增模型时，复用选定策略已有且有效的 chunk/BM25，只构建选中模型的向量；不自动调用其他模型。
- 修改切块规则时构建对应的新切块索引，保留其他策略的索引。
- 每套索引保存自己的来源版本和同步状态；不能用新来源元数据拼接旧 chunk。同步发现源文件变化或删除后，其他受影响索引须标记失效或移除对应旧数据，查询时明确要求同步，不声称其仍是当前快照。
- 查询只读取选中的切块索引及模型向量；缺少该组合或状态失效时明确报告。仅调整 RRF、topk 等召回参数不重切块、不重新 embedding。
- 现有单套索引迁移保留来源、定位和向量，按可验证的旧指纹登记；无法确定兼容关系的旧索引要求显式同步，不猜测归属。迁移失败回滚，先用隔离临时数据库验证。

## 替代范围与当前事实

本决定扩展[项目基线的定制能力](baseline.md)，修订[当前配置契约](../design/configuration.md)的单库单套切块/模型限制，并替代讨论中“每个模型配置档另存召回参数”的建议。其他已确认产品约束继续适用，旧文档保留为当前实现或历史依据。

当前代码仍是一份配置一个 embedding、同库一套 chunk/FTS/向量表；多份配置只有使用不同数据库时才能保留各自索引。此次记录没有实施数据库迁移、多配置选择或索引重建。
