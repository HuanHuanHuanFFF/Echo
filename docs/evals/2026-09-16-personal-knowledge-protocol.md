# 个人知识库默认方案评测协议

日期：2026-09-16。状态：已确认题量与场景划分；语料、标签与执行工具尚待完成。
本文落实[执行决定](../project/2026-09-16-evaluation-revision.md)，
不把计划或本地冒烟结果记为真实检索效果。具体配额以[JSON](2026-09-16-question-allocation.json)为准。

## 语料与抽样

选择3–4份独立真实笔记来源，目标约500–800篇Markdown。中文及中英混写优先，纯英文结果单列。
A/B/C/D是资料分组；若某组包含多个作者库，应分别记录其来源和结果。

| 组       | 形态                                    | 分库开发题 | 分库最终题 |
| -------- | --------------------------------------- | ---------: | ---------: |
| A        | 现有AI整理的个人学习、主题与复习笔记    |         30 |         50 |
| B        | 外部TIL、排障、代码片段、项目备忘       |         25 |         35 |
| C        | 读书/课程笔记、文章摘录、长文和混合结构 |         15 |         25 |
| D        | 完全不参与开发的独立知识库              |          0 |         30 |
| 分库合计 |                                         |         70 |        140 |

保留无/少标题、深层标题、短随手记、长段落、代码、列表、表格及版本边界等真实结构。
不预先翻译或统一改写风格。合成超长行等压力样本单列，不能冒充真实用户题。
每份来源记录URL、提交/下载时间、文件清单、使用许可、原文/副本哈希与同源转载关系；
公开不等于已证明纯人工创作。外部仓库是数据，不执行其脚本或指令。

候选形态参考是[个人TIL](https://github.com/simonw/til)和
[Blue Book个人wiki](https://github.com/lyz-code/blue-book)；尚未选定入库，仍需中文来源与独立留出库。
首版范围保持本地Markdown，资料中的外链、frontmatter专门检索等未实现能力须明确列为边界。

## 正式场景与配对

| 场景     | 开发 | 最终 |
| -------- | ---: | ---: |
| 分库     |   70 |  140 |
| 混合库   |   30 |   60 |
| 唯一问题 |  100 |  200 |

| 混合题主要考察点                  | 开发 | 最终 |
| --------------------------------- | ---: | ---: |
| 答案在一库，其他库有相似/无关干扰 |    9 |   18 |
| 必须跨库组合证据                  |   12 |   24 |
| 相似、重复、版本或适用条件不同    |    6 |   12 |
| 全混合范围仍无答案                |    3 |    6 |

分库搜索每库全部入选笔记，不按答案文件或题目主题预过滤。混合库不传答案所属来源提示。
开发混合范围是A+B+C，最终是A+B+C+D；最终混合20题须依赖D的证据，加D分库30题共50题。
每库与混合场景使用独立SQLite、共享策略配置；不得分别调出各库的最佳参数再汇报为默认结果。

从分库开发题选20题、最终题选40题，在混合范围额外复跑：
同一query_id、必需事实、预算和配置，变化单列。
300道独立题对应每个方案360次场景执行；额外复跑不增加独立样本或正式混合30%的分母。
干扰配对需在混库前后保持必需事实不变，混库新增的有效替代证据提前标注。
若可答性发生变化，归为跨库覆盖/条件辨析，不能充当纯干扰对照。

## 固定首轮配置

| 配置                                | 值                                                                |
| ----------------------------------- | ----------------------------------------------------------------- |
| chunk                               | heading-1000 / bagu-paragraph-800-lines                           |
| tokenizer                           | icu-zh，zh-CN，无自定义词典                                       |
| embedding                           | qwen3.7-text-embedding，1024维，send_dimensions=true              |
| API                                 | 阿里云兼容接口；batch_size=8、timeout_ms=30000，文档/查询前缀为空 |
| mode                                | hybrid，无rerank                                                  |
| topk / max_chunks_per_source        | 8 / 2，同时作为硬上限                                             |
| bm25_candidates / dense_candidates  | 60 / 60                                                           |
| rrf_k / bm25_weight / dense_weight  | 60 / 1 / 1                                                        |
| title_weight / min_dense_similarity | 2 / 0.3；阈值尚未针对新模型校准                                   |
| 每题累计上下文                      | 12000个UTF-16字符                                                 |

模型URL、实际模型名、维度、前缀、变换及版本进入快照，密钥只保留环境变量名。
固定qwen模型上的结果不能直接外推到其他embedding模型。

heading-1000沿用产品整行/1000字符软上限规则。
bagu-paragraph-800-lines按标题与段落组织，估算token目标300/800/1000，目标80字符行对齐重叠；
为了保留完整原文行，单个超长行可超过目标，不复制整块或携带过大的尾部。
它不是旧Java/Python逐字等价移植，当前是本地实验策略，尚未作为默认策略发布。
两者的原文定位契约沿用[v2配置](../design/configuration-profiles.md)。

Echo的max_context_chars只限制返回JSON。评测驱动器还须扣除请求、此前响应和实际宿主补读的
请求/响应，保证每题累计不超12000；字符预算不能称为token预算。
主检索比较与宿主补读增益分列；不能先多次取证再只统计最后一段正文。
原问题、子问题及同义变体在对照前冻结；Agent实时改写属于另一个端到端实验。

## 标签、划分与判分

每题保存query_id、intent_group、题型、场景、语料快照、可答性、必需事实、
允许替代证据及原文位置。标签绑定事实和原文，不绑定某种chunk ID。
若分级排序指标采用nDCG，必须另冻结相关性等级和去重规则，不能拿来源名命中代替相关性。

先从原文建立标签，再运行对照。两位Agent独立核对支持关系，分歧回到原文；
标注与复核时隐藏候选方案名称和胜负结果，避免方案偏好影响标签；
未执行人工审核时如实标注AI生成/复核，不写人工金标。
无答案题须在该场景完整资料范围核查，区分“未找到”和有根据的库内缺失。
D的查询、标签和效果不得参与调参，允许不使用检索分数的导入/定位工程检查。

同一知识点/近重复问法同组划分，开发100与最终200不交叉。
开发前冻结测试集与标签哈希；查看最终结果后再据此优化，则这版测试材料转为开发材料，
须另留新测试集。有效独立组数不足时报告缺口，不靠改写凑满300题。

主指标为相同预算下的必需事实覆盖、全部必需事实齐全的可答题比例。
辅助记录候选覆盖、MRR@8、来源集中、排名/阈值/来源上限/预算造成的遗漏。
无答案题单列：Echo返回非空不自动等于幻觉，Echo本身不生成答案。
Agent答案质量只在实际执行的Agent任务中评价，不能归为检索模型效果。

分库、混合、各库/题型和配对变化分别报告。可按预先确定的70%/30%给出场景汇总，
但不能只展示掩盖退化的平均数。
以独立意图组为单位作配对比较和重采样，报告差值及95%区间；具体计算器需先验证，
题量本身不保证显著。延迟按P50/P95报告，并说明预热、缓存、API、本地和传输边界。

## 实验与交付

先在开发集比较两种chunk，再补BM25-only/dense-only/hybrid对照和单组参数实验。
所有尝试、失败、部分降级与退化保留；query向量复用必须记录缓存条件。
冻结候选和基准后运行最终集，不在最终集上反复择优。

正式API调用前记录输入规模和本轮额度保护，发送前检查请求额度；
成功及失败都保存实际请求数、文本数、输入字符与服务报告tokens，未知用量不记为零。
普通CI不运行私有语料或真实API。现有npm run eval只支持仓库固定样本，
不能用其成功替代本协议的跨库300题执行。

交付包括代码/构建/策略/配置/语料/标签指纹、可重跑入口、逐题结果、
统计区间、实际成本、改进/退化/未解决案例和Agent工具流程记录。
私有正文和标签留在本地；公共汇总应明确哪些结果依赖非公开语料，不能宣称仅凭仓库即可完整复算。

方法参考：[BEIR](https://arxiv.org/abs/2104.08663)的多任务、多架构比较；
[检索评测统计推断](https://www.sciencedirect.com/science/article/pii/S0306457397000277)的区间估计。
本项目题量及配额是用户确认的应用设计，不是文献规定的门槛。
